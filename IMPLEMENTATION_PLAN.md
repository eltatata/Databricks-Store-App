### Rejected alternatives (do not reintroduce without a new decision)
- **Agent Bricks Supervisor Agent:** not available on Free Edition (dependencies unsupported), and it cannot call the app's in-process CRUD services.
- **Supervisor API (`/ai-gateway/mlflow/v1/responses` with hosted tools):** **end of life on 2026-09-30.** This also rules out AppKit's `DatabricksAdapter.fromSupervisorApi` backend.
- **Agent Bricks CLI (`agentbricks`, Beta, Python):** a separate deployment to the agent runtime that would duplicate Lakebase access. Revisit only if the AppKit `agents()` plugin proves unusable.
- **Two apps (separate frontend/backend):** no benefit and wastes quota.

# 1. Free Edition constraints (design inputs, verify in Phase 0)

| Area | Limit | Design impact |
|------|-------|---------------|
| Apps | **3 apps per account**; each app **auto-stops 24 h** after start/update/redeploy | Exactly one app. Runbook includes `databricks apps start`. |
| Lakebase | **1 project per account**, scale-to-zero | Reuse the existing project if one exists. One branch (`production`) plus short-lived dev branches only if needed. |
| SQL warehouse | **1 warehouse, 2X-Small** | Used by Genie and ad-hoc validation only. The app does not use it. |
| Pipelines | **1 active pipeline per pipeline type** | One SDP pipeline for the whole medallion. **Risk:** every synced table creates a managed pipeline, so refresh them sequentially in Snapshot mode (§5.3). |
| Jobs | **5 concurrent job tasks** per account | Linear job DAG. |
| Compute | Serverless only, limited size; restricted outbound internet | Kaggle download happens **locally**, then upload to a UC Volume. |
| Model Serving / FM APIs | Limited endpoints; "certain models are unavailable"; no provisioned throughput | **Model availability is unknown until Phase 0.** Pick a streaming, tool-calling chat endpoint actually listed in the workspace. |
| Agent Bricks | Knowledge Assistant unsupported; Supervisor Agent reported unavailable | See rejected alternatives. |
| Quota | Fair-use: exceeding it shuts compute down for the day | Small data, manual/on-demand runs, no schedules by default. |

# 2. Autonomous workflow and safety rules

## 2.1 Inspect first
1. Inspect the repo, `CLAUDE.md`/`AGENTS.md`, `skills-lock.json` and the installed skills under `.claude/skills/` (databricks-core, -apps, -lakebase, -pipelines, -jobs, -dabs, -genie-agents). **Load the matching skill before each phase.**
2. CLI: `databricks -v` (currently v1.20.0; `--auth-mode` needs ≥ v1.20.0; Lakebase needs ≥ v0.294.0). `databricks auth profiles`. **Never auto-select a profile.** Confirm with the user (the known profile is `local-dev`). Always pass `--profile`.
3. Run read-only discovery first (`-h`, `list`, `get`). Record results in `docs/ENVIRONMENT_AUDIT.md` as: confirmed / missing permission / not available on plan / not verified.
4. Verify every command against `-h` output and the current docs. Do not copy old syntax.

## 2.2 Approval gates (ask the user first)
- Deleting or overwriting any workspace resource, schema, table, Lakebase project/branch/schema, app, job, pipeline or volume.
- `DROP SCHEMA … CASCADE` in Lakebase (e.g. schema-ownership recovery). Offer export first.
- Pipeline **full refresh**.
- First `databricks apps deploy` and any later deploy.
- Creating resources with unclear cost, or changing workspace-wide settings or permissions.

## 2.3 Secrets
- Never commit tokens, `.env` or `server/.env`, Kaggle credentials, or downloaded raw data. Commit a safe `.env.example`.
- Local CLI uses OAuth (`databricks auth login`). The deployed app uses its service principal plus injected env vars (`PGHOST`, `LAKEBASE_ENDPOINT`, `DATABRICKS_GENIE_SPACE_ID`, `DATABRICKS_SERVING_ENDPOINT_NAME`). Never hardcode workspace IDs in source.
- Nothing secret reaches the React bundle.

## 2.4 Honest reporting
Distinguish "implemented locally", "tested locally", "deployed" and "verified end-to-end". Never simulate an unavailable feature.

## 2.5 Single repository: everything lives here (D13)

This repository is the only source of truth for the whole project:
- data ingestion, SQL, pipelines and jobs;
- Unity Catalog objects;
- Lakebase project, synced tables, grants and indexes, plus the app-owned schema migrations;
- the Genie space definition and benchmarks;
- the app (backend, frontend, agent, tools);
- Databricks configuration (bundles, `app.yaml`), operational scripts and documentation.

Nothing is created by hand in the UI without a matching file here. If a step can only be done in the UI, it is written down as a runbook step in `docs/DEPLOYMENT.md`.

### 2.5.3 Conventions
- **Three DAB bundles, deployed in order:** `data/` → (run the data job) → `serving/` → `app/`.
  - Each bundle deploys cleanly on a fresh workspace because its dependencies already exist.
  - `app/` keeps the bundle AppKit generates so `databricks apps init/validate/deploy` work unmodified.
  - Do not merge them into a root bundle.
  - Fresh-workspace order: `catalog-create.sh` → `data-deploy.sh` → `dataset-upload.sh` → `data-run.sh` → `serving-deploy.sh` → `serving-run.sh` → app (Phase 6).
- **No extra tooling layers:** no Terraform, no root `package.json` workspace, no Makefile. The bash scripts in `scripts/` are the single entry points, and each one is runnable alone.
- **Scripts are idempotent:**
  - `set -euo pipefail`, plus "create if missing, otherwise update".
  - They read non-secret config from `.env` and `DATABRICKS_PROFILE`, always pass `--profile`, and print what they changed.
  - Destructive actions are never automatic (§2.2).
- **Declarative first:** resource specs live in `.yml`/`.json`/`.sql` files; scripts only apply them.
- **File naming:**
  - kebab-case for scripts, YAML and JSON;
  - snake_case for SQL dataset files and Python;
  - `<feature>.<layer>.ts` on the server (§6.4);
  - PascalCase for React components (§6.6).
- **`.gitignore`:** `.env`, `.env.*` (except `.env.example`), `app/server/.env`, `.local/`, `.databricks/`, `node_modules/`, `dist/`, `build/`, `__pycache__/`, `.venv/`, `.pytest_cache/`, `*.zip`, `*.csv`.
- **Git:** initialize in Phase 0. One commit per coherent step, Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, `test:`).

## 2.6 Code quality: clean code, no comments (D11)
Applies to every language in the repo (TS, SQL, Python, bash). The frontend and backend also follow §6.4 and §6.6.

- **No comments in code.** That means no inline, block, JSDoc or docstring comments, no TODO/FIXME, and no commented-out code. If code needs a comment to be understood, rename or extract until it does not.
  - Exception 1: Unity Catalog `COMMENT` clauses on tables and columns are data that Genie consumes, not code comments, so they are required.
  - Exception 2: prose files (`*.md`, agent `instructions.md`) are content, not code.
- **Naming carries the meaning:**
  - functions are verb + noun (`getProductById`, `deactivateProduct`, `buildPaginationMeta`);
  - booleans start with `is`/`has`/`can`/`should`;
  - collections are plural;
  - no abbreviations except universal ones (`id`, `url`, `db`);
  - constants are `UPPER_SNAKE_CASE`, types are `PascalCase`;
  - names reflect the domain (`gmv`, `averageOrderValue`, `lateDeliveryRate`).
- **Small, single-purpose functions** with early returns. No nested ternaries, no magic numbers or strings (use named constants), no dead code, no unused exports.
- **Explicit types at module boundaries:** exported functions declare parameter and return types; no `any`.
- **Formatting and lint:** keep the formatter and linter the AppKit scaffold ships (ESLint/Prettier, `appkit lint`) and do not disable rules inline. Use ruff for Python and shellcheck for bash.
- **Review gate:** before closing any phase, scan the changed files for comments and rename or extract until none are needed.

- **Source:** https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce (author: Olist). License: **CC BY-NC-SA 4.0** (confirmed on the Kaggle page by the user, 2026-10-09). Record it in `docs/DATASET.md`. Do **not** commit the raw CSVs.
- **Files (verify actual names and row counts):**

| File | Entity | Approx. rows |
|------|--------|--------------|
| `olist_orders_dataset.csv` | orders | ~99k |
| `olist_order_items_dataset.csv` | order items | ~113k |
| `olist_order_payments_dataset.csv` | payments | ~104k |
| `olist_order_reviews_dataset.csv` | reviews | ~99k |
| `olist_customers_dataset.csv` | customers | ~99k |

| `olist_geolocation_dataset.csv` | zip-prefix geo | ~1M (**optional**, skip in v1 unless needed) |

- **Known caveats to handle and document:**
  - Currency is BRL. Orders span roughly 2016-09 to 2018-10; source timestamps have no time zone, so treat them as `America/Sao_Paulo` local time (`TIMESTAMP_NTZ`).

  - Reviews contain duplicate `review_id`s across orders. Review text is free Portuguese text with no PII expected; drop it from Gold.
  - **Products have no human-readable names.** For the app, `display_name` is a **derived label** (e.g. `"<category_en> · <first 8 chars of product_id>"`), clearly documented as synthetic.

| Volume | `data_engineering.bronze.landing` | Layout: `/Volumes/data_engineering/bronze/landing/olist/<entity>/<file>.csv` (one folder per entity, so Auto Loader reads a stable schema per folder). |

## 4.2 Pipeline: one Lakeflow Spark Declarative Pipeline (SQL, serverless)
- Load the `databricks-pipelines` skill. Use modern syntax only: `CREATE OR REFRESH STREAMING TABLE / MATERIALIZED VIEW`, `STREAM read_files(...)`, no `LIVE.`.
- One dataset per file under `data/pipeline/{bronze,silver,gold}/`.

**Bronze: streaming tables with Auto Loader** (one per entity: `bronze.orders_raw`, `bronze.order_items_raw`, …)
- `FROM STREAM read_files('/Volumes/.../olist/<entity>/', format => 'csv', header => true, ...)`, with all columns kept as STRING, plus `_metadata.file_path AS source_file`, `_metadata.file_modification_time`, and `current_timestamp() AS ingested_at`. `_rescued_data` is retained.
- Idempotency comes from Auto Loader's file checkpointing: re-running does not re-ingest already-processed files. Document that re-uploading a **changed** file under a new name appends a new batch.
- No business fixes in Bronze.

**Silver: typed, cleaned, conformed**

| Table | Grain / PK | Key rules |
|-------|-----------|-----------|
| `silver.orders` | `order_id` | Cast 5 timestamps; `order_status` normalized lowercase; expectation that purchase timestamp is not null. |
| `silver.order_items` | (`order_id`, `order_item_id`) | `price > 0`, `freight_value >= 0`; FK-style expectation on `order_id`. |
| `silver.payments` | (`order_id`, `payment_sequential`) | `payment_value >= 0`; `payment_type` normalized. |
| `silver.reviews` | `review_id` + `order_id` | Score 1–5; dedupe deterministically (latest `review_answer_timestamp`). |
| `silver.customers` | `customer_id` (also keep `customer_unique_id`) | Trim, uppercase state codes. |
| `silver.sellers` | `seller_id` | Same. |
| `silver.products` | `product_id` | Rename typo columns; join translation → `category_en` (`'unknown'` only where the source category is null, with a flag column `category_missing`). |

- Use expectations: `EXPECT … ON VIOLATION DROP ROW` for hard rules. Write rejected rows to `silver.<entity>_quarantine` through an inverse-condition MV with a `reject_reason` column.
- Silver is a clean relational model, not an OLTP schema.

**Gold: materialized views, analytical serving model**

| Table | Grain / PK | Purpose | Synced to Lakebase? | In Genie? |
|-------|-----------|---------|---------------------|-----------|
| `gold.fact_sales` | (`order_id`, `order_item_id`) | Item-level fact with order dates, status, customer state, seller, category, price, freight, review score | No (Genie only) | ✅ |
| `gold.fact_orders` | `order_id` | Order-level fact: status, validity, dates, delivery, item/seller counts, GMV, freight, payments, latest review. Single source for order-grain KPIs | No (Genie only) | ✅ |
| `gold.dim_product` | `product_id` | Curated catalog: `category_en`, dimensions, weight, derived `display_name` | ✅ (seed source for `app.products`) | ✅ |
| `gold.kpi_daily` | `order_date` | Orders, items, GMV, freight, distinct customers per day, AOV, avg review, additive `reviewed_orders`/`review_score_sum`, late-delivery counts and rate | ✅ | ✅ |
| `gold.customer_activity_daily` | (`order_date`, `customer_unique_id`) | One row per customer and day with a valid order. Exact distinct customers for any date range | ✅ | No |
| `gold.sales_by_category_month` | (`month`, `category_en`) | Revenue/units/orders by category | ✅ | ✅ |
| `gold.sales_by_state_month` | (`month`, `customer_state`) | Geographic breakdown | ✅ | ✅ |
| `gold.product_performance` | `product_id` | Units, revenue, orders, avg review, first/last sale, rank | ✅ | ✅ |
| `gold.seller_performance` | `seller_id` | Revenue, orders, avg review, late-delivery rate | ✅ | ✅ |

- Keep slice dimensions (date, category, state, seller) and do not over-aggregate.
- Add table and column `COMMENT`s (they feed Genie).
- All KPI formulas live in `docs/KPIS.md`. Minimum set:
  - **GMV** = Σ `price` over items of orders with status ≠ `canceled`/`unavailable`.
  - **Freight** = Σ `freight_value` (reported separately).
  - **Orders** = count distinct `order_id` (same filter).
  - **AOV** = GMV / Orders.
  - **Distinct customers** use `customer_unique_id`.
  - **Late-delivery rate** = delivered orders where `delivered_customer_date > estimated_delivery_date` / delivered orders.
  - **Avg review** = mean `review_score` per order (deduped).
  - State the BRL currency, the Sao Paulo time-zone assumption, and that canceled orders are excluded.

## 5.3 Synced tables (Gold → Lakebase)
- **Declared in DABs (D15)** as `postgres_synced_tables` in `serving/resources/lakebase.yml`. Never use the legacy `synced_database_tables`. The first table creates the sync pipeline (`new_pipeline_spec`); the rest reuse it (`existing_pipeline_id`). Fallback if the Beta resource fails: `databricks postgres create-synced-table` from a script.
- **Snapshot mode.** Gold MVs are small and recomputed fully, and Triggered/Continuous require CDF. Refresh is driven by the job (§4.3) by triggering the single shared sync pipeline, which respects the "1 active pipeline" limit. If the Free Edition pipeline limit blocks synced-table pipelines, record it and fall back to syncing fewer tables (`kpi_daily`, `sales_by_category_month`, `product_performance`, `dim_product`).

  `GRANT USAGE ON SCHEMA serving …; GRANT SELECT ON ALL TABLES IN SCHEMA serving …; ALTER DEFAULT PRIVILEGES IN SCHEMA serving GRANT SELECT ON TABLES …` to the service principal's client ID (from `databricks apps get`).
- Create Postgres indexes for app query paths (e.g. `kpi_daily(order_date)`, `product_performance(revenue DESC)`). Index creation is allowed on synced tables.
- Constraints to respect: no null bytes in strings; no VARIANT/GEOGRAPHY columns; null PKs are dropped; schema changes must be additive.

## 5.4 Writable model (`app` schema)

The source of truth is the Drizzle schema `app/server/database/schema/app.schema.ts` (`pgSchema('app')`). `drizzle-kit generate` derives the SQL migrations from it. The resulting DDL must be equivalent to:

```sql
app.products(
  product_id     TEXT PRIMARY KEY,
  display_name   TEXT NOT NULL CHECK (length(display_name) BETWEEN 1 AND 200),
  category_en    TEXT NOT NULL,
  weight_g       INTEGER CHECK (weight_g >= 0),
  length_cm      INTEGER CHECK (length_cm >= 0),
  height_cm      INTEGER CHECK (height_cm >= 0),
  width_cm       INTEGER CHECK (width_cm >= 0),
  list_price_brl NUMERIC(12,2) CHECK (list_price_brl >= 0),
  is_active      BOOLEAN NOT NULL DEFAULT TRUE,
  source         TEXT NOT NULL CHECK (source IN ('olist_seed','app')),
  created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  version        INTEGER NOT NULL DEFAULT 1
);
app.audit_log(
  id          BIGSERIAL PRIMARY KEY,
  actor_email TEXT NOT NULL,
  channel     TEXT NOT NULL CHECK (channel IN ('ui','agent')),
  action      TEXT NOT NULL,
  entity      TEXT NOT NULL,
  entity_id   TEXT NOT NULL,
  before      JSONB,
  after       JSONB,
  at          TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

- `product_id` is the Olist id for seeded rows and a UUID for products created in the app.
- `list_price_brl` is seeded from the median item price in the source data.
- `is_active` implements soft delete. `version` implements optimistic concurrency.
- Indexes: `products(category_en)`, `products(is_active)`, an index for name search (`lower(display_name)`, or trigram if `pg_trgm` is available), and `audit_log(entity, entity_id, at)`.

- **Seed:** an idempotent `INSERT INTO app.products … SELECT … FROM serving.dim_product ON CONFLICT DO NOTHING` (Drizzle `insert().select()` or its parameterized `sql` template), run once by an explicit admin endpoint or script (not on every boot).
- **Delete** is a soft delete (`is_active=false`). A hard delete is allowed only for `source='app'` rows.
- An optional second CRUD entity (e.g. `app.sellers`) is added only after products is complete.

## 6.4 Backend: layered MVC, functional style (D9)

### 6.4.1 Rules
- **Flow:** `route → middlewares (validate, context) → controller → service → database (queries)`. Each layer only calls the next one down. Controllers never touch SQL, and services never touch `req`/`res`.
- **Functional modules, no OOP.**
  - Every module exports plain functions; no classes, no `this`, no DI containers or decorators, no ports/adapters, no repository interfaces with multiple implementations.
  - Collaborators are imported directly (`import * as productsService from '../services/products.service'`).
  - **Only exception:** one minimal `AppError` class in `utils/errors.ts`, because `instanceof` and stack traces need it. It is created only through factory functions.
- **Shared state:** the Drizzle instance is created once at startup in `database/client.ts` (`initDatabase(appkit.lakebase.pool)` → `drizzle(pool, { schema })`) and read through exported helpers (`getDb`, `withTransaction`). Nothing else is global.
- **Types:**
  - `schemas/` holds Zod schemas, the single source for request validation, inferred types (`z.infer`) and OpenAPI docs.
  - `interfaces/` holds non-validated types: service results, the API envelope, `RequestContext`. DB row types are inferred from the Drizzle tables (`$inferSelect` / `$inferInsert`) and re-exported from `interfaces/`, never written by hand.
  - Zod schemas (API contract) and Drizzle tables (storage) are kept separate on purpose. No `drizzle-zod`; services map between them.
  - No `any`, and no `as unknown as T` (blocked by `appkit lint`). Narrow with Zod or typed mappers.
- **Reuse:** generic helpers live in `utils/` (pagination, sort allowlists, async handler, response builders, logger, DB error mapping). Agent tools reuse services.
- **Naming:** `<feature>.<layer>.ts` (e.g. `products.controller.ts`, `products.service.ts`, `products.queries.ts`, `products.schema.ts`, `product.interface.ts`).

### 6.4.3 Validation (Zod)
- Every route declares `validate({ params, query, body })` with schemas from `schemas/`. Controllers receive already-parsed, typed data and never re-validate.
- Body schemas are `.strict()` (unknown keys are rejected). Query numbers use `z.coerce` with bounds (e.g. `pageSize` 1–100). Sorting is an enum from the allowlist.
- Agent tool inputs reuse the same Zod schemas as the REST bodies, so the rules exist once.
- `config/env.ts` validates environment variables at boot. The app refuses to start if a required variable is missing, and the message names the variable, not its value.

### 6.4.4 Swagger / OpenAPI
- Generate the OpenAPI 3 document from the Zod schemas.
  - With **Zod v4**, use `@asteasolutions/zod-to-openapi` ≥ v8, with metadata via `.meta()`.
  - With **Zod v3**, use v7.3.4.
  - **Use the Zod version AppKit already depends on.** Check `pnpm why zod` before installing.
- `docs/openapi.ts` registers every path with its request schemas, response schemas and error responses (400/404/409/422/500 using the common error envelope).
- Serve **Swagger UI** at `/api/v1/docs` (`swagger-ui-express`) and the raw spec at `/api/v1/openapi.json`. Both sit behind Databricks Apps authentication, like the rest of the app.
- Every route is a `RouteDefinition` (method, path, request schemas, responses, handler) in `routes/*.routes.ts`. Express registration and the OpenAPI document are both built from that single list, so the docs cannot drift. A test still asserts full coverage.

### 6.4.5 Errors and exceptions
- **Custom errors:** `AppError { status, code, message, details?, expose }` is created only through the factories in `utils/errors.ts`. Codes are a closed union (`VALIDATION_ERROR`, `NOT_FOUND`, `CONFLICT`, `VERSION_CONFLICT`, `UNPROCESSABLE`, `DB_UNAVAILABLE`, `INTERNAL_ERROR`).
- **Where `try/catch` is used (and nowhere else):**
  - `database/client.ts` → `withTransaction(fn)`: wraps `db.transaction(fn)` (Drizzle rolls back when `fn` throws) and rethrows through `mapDbError`.
  - `database/client.ts` → a shared `runQuery(fn)` helper used by every function in `queries/`: catches driver errors (Drizzle keeps the pg error, with its code, as the `cause`) and rethrows them as `AppError` via `utils/db-errors.ts`. Raw pg messages never leave the database layer.
  - Services throw `AppError` for business-rule failures (not found, inactive product, version mismatch). They do not catch errors just to log them.
  - Agent tools catch `AppError` and return `{ ok: false, code, message }` to the model. Unknown errors become a generic tool failure.
- **Controllers have no `try/catch`.** AppKit 0.84 ships Express 4.22, so every async controller is wrapped in `asyncHandler`, which forwards rejections to `next(err)`.
- **Global error handler** (`error.middleware.ts`, registered last on the `/api/v1` router):
  - `ZodError` → 400 with field issues.
  - `AppError` → its status and code.
  - `SyntaxError` from the JSON parser → 400.
  - Anything else → 500 `INTERNAL_ERROR` with a generic message.
  - It always includes `requestId` and logs the full error server-side (stack included). Stack traces never go to the client.
- **Not-found handler:** 404 for unmatched `/api/v1/*`. It is scoped to the router, so it never intercepts AppKit plugin routes (`/api/genie/*`, `/api/agents/*`) or the SPA.
- **Process level** (end of the chain):
  - `process.on('unhandledRejection')` and `process.on('uncaughtException')` log the error and exit with a non-zero code so the platform restarts the app.
  - AppKit's lifecycle manager owns `SIGTERM`/`SIGINT` and `process.exit`, so the app does not register its own signal handlers.
- **Response envelope:** success is `{ data, meta? }`; error is `{ error: { code, message, details?, requestId } }`.

### 6.4.6 Other backend rules
- All database access goes through Drizzle's query builder, or its `sql` tagged template for complex aggregations (still parameterized). No string-concatenated SQL. Dynamic `ORDER BY` maps allowlisted keys from `config/constants.ts` to Drizzle columns.

### 6.4.7 Drizzle ORM (D14)
- **Packages:** `drizzle-orm` (runtime) and `drizzle-kit` (dev).
  - The driver is a dedicated `pg.Pool` built from `appkit.lakebase.getPgConfig()` (D14 amendment), with `drizzle-orm/node-postgres`.
  - Never build a connection string or a static password: OAuth token refresh comes from AppKit's config (password callback).
  - Check `npx @databricks/appkit docs ./docs/plugins/lakebase.md` for `pool` / `getOrmConfig()`.
- **Two schemas, two roles:**
  - `app.schema.ts`: writable tables, and the only input to `drizzle-kit`.
  - `serving.schema.ts`: typed declarations of the synced Gold tables, read with `select` only. It is excluded from `drizzle.config.ts` (`schema` points only at `app.schema.ts`; `schemaFilter: ['app']`), so migrations can never create, alter or drop synced tables.
- **Migrations:**
  - `drizzle-kit generate` needs no DB connection. It writes SQL migrations to `database/migrations/`, and they are committed.
  - At startup, `runMigrations()` calls Drizzle's `migrate(db, { migrationsFolder, migrationsSchema: 'drizzle', migrationsTable: '__drizzle_migrations' })`.
  - Migrations run as the app service principal, so it creates and owns `app` (§5.2).
  - **Never** run `drizzle-kit push` or `drizzle-kit migrate` against Lakebase from a local machine. Objects would be owned by the developer and the app would lose access.
  - Make sure the migrations folder ships in the deployed app (copy it in the server build if `tsdown` does not).
- **Read-only guard:** `serving` tables are imported only by `dashboard.queries.ts` and the seed query. A test asserts that no `insert`/`update`/`delete` targets a `serving` table.
- **Transactions:** `db.transaction(async (tx) => ...)`. Query functions accept an optional executor (`tx` or `db`), so services can compose several queries in one transaction.
- **Optimistic concurrency:** update `products` with `version = version + 1` and `updated_at = now()` where `product_id` and `version` both match, using `.returning()`. Zero rows → `VERSION_CONFLICT` (or `NOT_FOUND` if the product does not exist).
- **Testing:** unit tests mock `database/queries/*`. Opt-in integration tests run the real migrations and queries against a short-TTL Lakebase dev branch.
- JSON body parsing and its size limit belong to AppKit's server plugin (default 1 MB, `server({ bodyLimit })`). Malformed or oversized bodies are mapped to 400/413 by the global error handler. No CORS (same origin).
- `GET /api/v1/health` reports the Lakebase ping and migration version, with no secrets.

### 6.6.3 Rules

# 7. Agentic AI

## 7.1 Components
- **Supervisor:** an AppKit code agent at `server/agents/supervisor/agent.ts` (`createAgent`, `@databricks/appkit/beta`). The model backend is `databricks-qwen3-next-80b-a3b-instruct` (fallback `databricks-llama-4-maverick`), configurable through `AGENT_SERVING_ENDPOINT` (D16). It is bound as a `serving_endpoint` resource with `CAN_QUERY`, because Unity Gateway is not enforced on this workspace.
- **Genie Agent:** curated over `gold.*` (§7.4), exposed to the supervisor through the genie plugin toolkit (verify the exact toolkit name in the AppKit agents docs) and to users directly through the Explore page (`useGenieChat`). **Amendment (D19):** users reach Genie only through the assistant.
- **Tools** (Zod schemas, explicit `effect`):

| Tool | Effect | Calls |
|------|--------|-------|
| `ask_analytics` (Genie) | read | Genie Agent conversation (UC Gold) |
| `get_kpi_summary(from?, to?)` | read | `dashboardService.getSummary` (Lakebase `serving`) |
| `get_sales_by_state(from?, to?, metric?)` (D20) | read | `dashboardService.getStateBreakdown` (Lakebase `serving`); rendered as a state map |
| `search_products(query?, category?, limit≤20)` | read | `productsService.listProducts` |
| `get_product(product_id)` | read | `productsService.getProduct` |
| `create_product({display_name, category_en, …})` | write → **HITL** | `productsService.createProduct` |
| `update_product(product_id, patch, version)` | update → **HITL** | `productsService.updateProduct` |
| `deactivate_product(product_id)` | destructive → **HITL** | `productsService.deactivateProduct` |

- **HITL:** configure `agents({ approval: … })` so that **all** mutating tools require approval (not only destructive). Verify the option name in the docs. Approvals post to `/api/agents/approve` and must come from the same user who opened the stream. The timeout auto-denies.
- **Never** enable `lakebase.query` as an agent tool. There is no generic SQL tool and no model-supplied SQL, code or JSX.
- Audit: every tool mutation writes `audit_log` with `channel='agent'` and the requesting user's email.
- **Amendment (Phase 8):**
  - **Tool plugin:** AppKit runs a hand-rolled `tool({ execute })` as the service principal with no access to the request, so its audit rows could not carry the user's email. The Lakebase tools therefore live in a small ToolProvider plugin, `server/plugins/store-tools/` (`plugin.ts` + `tools.ts`, registered as `storeTools()` in `createApp`). Plugin tools run in the caller scope, so `getCallerContext().principal.userEmail` is available. The plugin exposes `toolkit()` because markdown agents resolve `plugin:<name>` only through it.
  - **Markdown agent:** the supervisor is `server/agents/supervisor/agent.md` (frontmatter tools + routing policy body) instead of `agent.ts` + `instructions.md`. A code agent is bundled as a separate entry, would duplicate the database client module, and gains nothing here.
  - **Genie tool:** `ask_analytics` is the Genie toolkit tool `olist.sendMessage`, renamed in the frontmatter.
  - **Argument schemas:** the serving endpoint rejects JSON Schema `pattern`, so the LLM-facing schemas (`server/schemas/agent-tools.schema.ts`) use plain types, and each tool re-validates with the REST Zod schemas.
  - **Approval timeout:** set by `AGENT_APPROVAL_TIMEOUT_MS` (default 120 s). Limits: 20 tool calls per run, 100 s per tool call.
  - **Threads:** the thread store stays the default in-memory store, so conversations are lost on restart. That is acceptable for a single-instance POC. A Lakebase-backed store is a stretch item.

## 7.2 Routing policy (in `instructions.md`)
1. Historical or analytical questions (trends, rankings, "why", cross-dimension slicing) → `ask_analytics`.
2. Headline KPIs or specific product lookups → Lakebase read tools (faster, deterministic).
3. Create/update/deactivate → resolve the target with `search_products`/`get_product`. Ask for missing required fields. Call the mutating tool, which triggers approval.
4. Ambiguous target or mixed incompatible requests → ask a clarifying question.
5. Out of scope → say so and list what is supported.
6. Instructions are trusted config. Never derive tool descriptions from user input.

## 7.3 Identity
- The app service principal runs Lakebase access and hand-written tools (AppKit hand-rolled `tool()` runs as the service principal).
- Genie tool calls run on behalf of the user if the `genie` scope is declared in `user_api_scopes`; otherwise as the service principal. Pick one in Phase 0 and record it. For a single-user POC either works, and the service principal is simplest.
- No roles (D6). Identity comes only from platform headers, never from the request body.
